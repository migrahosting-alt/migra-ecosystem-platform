## 🚨 Three production leaks found by running the pipeline

Each was found by *running* it against staging, not by reading it.

| # | where | what it did | commit |
| --- | --- | --- | --- |
| 1 | cutover restart **and the printed rollback command** | named `migrapilot-consumer.service` — production's unit | `50e2bcec` (overnight) |
| 2 | boot test | mounted `/etc/migrapilot/*.env` and `User=migrapilot` — production's configuration and service account | `aff08988` |
| 3 | **final verification** | curled `http://10.10.0.13:3000` — **production** — and asserted it carried the staging release | `f18db0fe` |

Leak 3 is the worst of the three. Every staging deploy failed its last step even after
succeeding and printed *"PRODUCTION IS SERVING A DIFFERENT COMMIT — roll back"* about a correct
release; and a staging deploy reached across to production on every run. Read-only, so nothing
changed — but the isolation the contract exists for was broken at the one link that decides
whether a human believes the deploy.

Two further clean-checkout defects blocked the pipeline before it could run at all:

- `docs/migrapilot/workspace-digest.mjs` — invoked by every release, **never tracked by git**.
  A clean checkout could not deploy. (`ed1571a2`)
- `apps/migrapilot-consumer/next-env.d.ts` is generated by `next build` and gitignored, while
  `npm run verify` typechecks **before** building — so `typecheck` fails on a fresh worktree.
  Worked around by pre-generating; **not fixed**, see open items.

## P0 validation 1 — LOCALITY

### Against the staging Brain (`staging-3c204aa8`, the PRE-FIX build)

Execution locality established from evidence — bytes on disk against advertised parameters,
and VRAM residency during generation — not from provider labels.

| class | model | disk | resident | VRAM | **locality** | declared |
| --- | --- | --- | --- | --- | --- | --- |
| fast | qwen2.5-coder:1.5b | 986 MB | yes | 2.1 GB | ON-DEVICE | local, cost 0 |
| balanced | llama3.1:8b | 4.9 GB | yes | 13.9 GB | ON-DEVICE | local, cost 0 |
| **deep** | **gpt-oss:120b-cloud** | **384 B** | **no** | **0** | **REMOTE** | **local, cost 0** |
| automatic | llama3.1:8b | 4.9 GB | yes | 13.9 GB | ON-DEVICE | local, cost 0 |
| coding | qwen2.5-coder:14b | 8.99 GB | yes | 15.3 GB | ON-DEVICE | local, cost 0 |
| reasoning | qwen3:8b | 5.2 GB | yes | 11.5 GB | ON-DEVICE | local, cost 0 |
| **profile=premium** | **gpt-oss:120b-cloud** | **384 B** | **no** | **0** | **REMOTE** | **local, cost 0** |
| explicit override | gpt-oss:120b-cloud | 384 B | no | 0 | REMOTE | local, cost 0 |

It generated a reply while holding **zero VRAM** and **384 bytes on disk**. Something produced
116.8B-parameter output without the weights being on the machine. That is the proof of actual
execution locality — no label was trusted.

The product's own **premium** profile maps to `deep`, so a user choosing the strongest model
was choosing off-device.

### Against the fixed registry, on the same live Ollama catalog

`apps/brain-service/scripts/locality-proof.mts`:

```
=== allowRemote=false (the shipped default) — catalog of 15 ===
    models classified REMOTE in the catalog: none
    gpt-oss:120b-cloud eligible: NO
    fast      -> qwen2.5-coder:1.5b   on-device  1.0 GB
    balanced  -> llama3.1:8b          on-device  4.9 GB
    deep      -> qwen3-coder:30b      on-device 18.6 GB
    explicit override "gpt-oss:120b-cloud" -> qwen3-coder:30b

=== allowRemote=true (explicit opt-in) — catalog of 16 ===
    models classified REMOTE in the catalog: gpt-oss:120b-cloud
    deep      -> gpt-oss:120b-cloud   hosting=remote  REMOTE (384 B for 116.8B params)
```

**Naming the cloud model explicitly does not reach it** — it is not in the catalog to be found,
so the override falls through to an on-device model. When allowed, it is labelled
`hosting: 'remote'`, never relabelled `local`.

🚨 **This fix is in the Brain and the Brain is NOT deployed** (see blocker below). The defect is
still live on staging.

## P0 validation 2 — PROVIDER HEALTH

No-inference state recreated safely on a spare port (`:3992`, `MIGRAPILOT_LOCAL_PROVIDER=stub`,
persistence off) against the fixed code. Staging was not touched.

```
FIXED CODE, no inference configured:
  overall status     : error          ← was "ok"
  inferenceProviders : unavailable    ← was "available"
  gpuCapacity        : ready / headroom-available
  local    reachable=False kind=stub  deterministic stub — no inference endpoint configured (set MIGRAPILOT_LOCAL_PROVIDER=…)
  cheap    reachable=False kind=stub  …
  default  reachable=False kind=stub  …
  premium  reachable=False kind=stub  …
```

A Brain with no generating path **cannot** report operational inference. The seven axes the
brief asked to keep distinct now are:

| axis | where it reads |
| --- | --- |
| configured | the provider is declared at all |
| reachable | `reachable` — an endpoint answered a probe |
| authenticated | `unknown` + "credential absent" |
| model available | `degraded` when reachable with zero models |
| **generation proven** | `kind: 'stub' \| 'live'` + the `stub` status — new |
| capacity ready | `gpuCapacity` / `gpuSignals` |
| routable | admission gate + router |

Note `gpuCapacity: ready` alongside `inferenceProviders: unavailable`: the GPU genuinely has
headroom and the Brain is genuinely not configured to use it. Two axes, correctly independent.

🚨 **Also Brain-side, therefore also not deployed.**

## Streaming cancellation — determination

**The current behaviour is safe but under-specified.**

A cancelled turn persists the user message and no assistant row. Nothing is invented, which
satisfies the hard rule. But the Brain's store already defines
`MessageStatus = 'complete' | 'partial' | 'failed'`, and the consumer's `appendMessage`
operation cannot carry a status at all — every row in staging is `complete` (112 user, 110
assistant). So the representation the brief asks for already exists in the schema and is
unreachable from the consumer.

Same root cause as the missing model attribution: the consumer's message-append contract is
narrower than the Brain's. Whether a cancelled turn should appear in the transcript is a product
decision, so it is reported rather than chosen.
