# Migra Email — Google Cloud setup (BONEX'S ACTIONS)

**Status: the code path is built and tested; no Google Cloud resource exists.**

Steps 1–7 of the ordered plan are complete and committed. This document is
step 8, and every action in it is yours: the agent must never create, request,
read back, or store these credentials.

Until the four environment variables below are set, the Brain logs
`EMAIL CONNECT DISABLED` with the specific reason and serves everything else
normally. Nothing is broken by not doing this yet.

## The exact values

Generated by `googleConsoleSetup()` in `apps/brain-service/src/engine/email/oauthConfig.ts`
and asserted exactly in test. **Do not retype these from memory** — if the
public origin ever changes, re-run the generator rather than editing this file,
because the code is the source of truth and this page is a copy.

For `MIGRAPILOT_PUBLIC_ORIGIN = https://chat.migrateck.com`:

| Console field | Exact value |
|---|---|
| Authorized redirect URI | `https://chat.migrateck.com/api/account/mail/callback` |
| Authorized JavaScript origin | `https://chat.migrateck.com` |

No trailing slash on either. The redirect URI must match **character for
character** — Google compares it literally, and a mismatch fails at a user's
sign-in with `redirect_uri_mismatch`, not at deploy time.

## What to create

1. **Google Cloud project** — your account, your choice of project. The console
   already had `migrapilot` selected when this was last checked.

2. **Enable the Gmail API** for that project.

3. **OAuth consent screen**
   - User type: whichever suits the account you are using.
   - Scopes: add **only** `https://www.googleapis.com/auth/gmail.readonly` for
     now. `gmail.compose` and `gmail.send` come later, deliberately — a consent
     screen asking for permission to send mail before the product has shown it
     can read any is asking for the irreversible permission on a promise.
   - `gmail.readonly` is a **restricted** scope. Until the app is verified,
     expect an unverified-app warning and a cap on how many accounts may
     connect. That is fine for qualification; it is a real constraint before
     any wider release.

4. **OAuth client ID**, type **Web application**
   - Enter the two values from the table above.
   - This produces a client ID and a client secret.

## Where the credentials go

Four variables, on the **Brain** (`/etc/migrapilot/brain.env`), never in the
repository and never in the consumer's environment:

| Variable | Value |
|---|---|
| `MIGRAPILOT_GOOGLE_CLIENT_ID` | from the console |
| `MIGRAPILOT_GOOGLE_CLIENT_SECRET` | from the console |
| `MIGRAPILOT_PUBLIC_ORIGIN` | `https://chat.migrateck.com` |
| `MIGRAPILOT_MAIL_TOKEN_KEY` | generate — see below |

### Generating the sealing key

Run this yourself. It writes 32 random bytes as base64. **Do not paste the
output into chat, a commit, or a screenshot.**

```sh
openssl rand -base64 32
```

This key encrypts every stored refresh token, and it is held **outside** the
database on purpose: a refresh token opens the user's actual mailbox from
anywhere, survives a Migra password change, and does not expire on its own, so
a database dump must not be a permanent key to every connected mailbox.

🚨 **Losing this key does not lose the mailboxes — it makes every stored
connection unopenable.** The code reports that as provider unavailability and
tells an operator, deliberately *not* as "reconnect": reconnecting would
overwrite good rows to work around a missing key and destroy the evidence.
Back it up wherever the other production secrets live.

🚨 **Changing this key has the same effect as losing it.** Rotation is possible
— the key id is stored beside each ciphertext, so "sealed with a different key"
is a distinguishable state — but a re-sealing pass would have to be written
first. There is none today.

## Verifying it worked

1. Restart the Brain. The log line should be `Email connect enabled.` If it is
   not, the same log names which of the three reasons applies (no OAuth client,
   no sealing key, no mail repository).
2. `GET /api/account/mail` as a signed-in user should answer `not_connected`.
3. Connecting should reach Google's consent screen showing **read-only** access.
4. After consent, the browser should land back in the app with `?mail=connected`.

Migration 27 and 28 must have run on the production database. Both are
append-only and were verified against a real PostgreSQL in the test suite, but
**applying them to production is a schema change and needs its own approval.**

Send tests are not built yet, so nothing here can send mail. When they are, the

## What is deliberately NOT requested yet

`gmail.compose` and `gmail.send`. Governed send exists in the engine and is
mutation-tested, but it is not wired end to end. Requesting send scope before
that is finished asks a user for the irreversible permission on the strength of
a promise, and the connection would carry an authority the product cannot yet
honour.
