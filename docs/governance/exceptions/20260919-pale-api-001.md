## Why this is V §5 and not V §4

This is **not** a security defect. Article V §4 promotes *security* defects independently of
feature releases; stretching it to cover an availability regression would misuse it. This
exception is written instead under V §5, which is the correct instrument for a bounded,
auditable operational change.

`pale-api` carries **no row** in `governance-status.json`. Per `services.migrapilot_consumer.note`,
*"Absence of a row is NOT compliance: under an active per-service freeze it fails closed."*
So `pale-api` is blocked by default, and a normal deployment is not available. Hence this
exception.

## Defect being remediated

Push-token registration has been returning **HTTP 400** for every released mobile build since
**2026-06-06** (mobile commit `f431c93`).

```
mobile POST /notifications/register  { token, platform, language }
RegisterPushTokenDto                 declares { token, platform }
ValidationPipe (main.ts)             forbidNonWhitelisted: true
result                               400 → Device.pushToken never stored
```

With no stored token, `sendCallRingWakeToUser()` finds `tokens.length === 0` and returns
without sending. Consequence for the already-distributed beta (build 144 / v0.1.30, on both
Play and sideload installs):

- no incoming-call wake when the app is backgrounded, swiped away, or the device is dozing;
- no background or killed-state text notifications;
- the entire out-of-process notification path silently disabled, estate-wide.

Foreground websocket delivery was unaffected throughout, which is why the outage went unseen.

Evidence: device log, S23 Ultra (`R5CW13Z4EJH`), 2026-09-19 14:07:34 —
`'[notifications.register_push]' AxiosError: Request failed with status code 400`,
followed 0.3s later by a healthy `socket.connected { transport: 'websocket' }`.

## Scope — the whole of it

**In scope:** `RegisterPushTokenDto` contract compatibility only — declaring the optional
`language` property the released client already sends, so the request validates.

- Files: `backend/src/modules/notifications/dto/register-push-token.dto.ts` and its spec.
- `language` is accepted and **not** persisted or read. It is a loose `@IsString()`, not an
  allow-list, because an allow-list would re-create the outage for any installed client
  holding a stale locale.

**Explicitly out of scope, and not included in the deployment:**

- `platform` validation — unchanged, still strict `@IsIn(["ios","android"])`.
- `forbidNonWhitelisted` — unchanged, still `true`. Unknown properties are still rejected.
- Any feature change, notification refactor, or localization persistence work.
- Any unrelated backend change.
- The five recovered mobile source files (`IncomingCallService.kt`, `notificationCopy.ts`,
  `notificationCopy.test.ts`, `supportContactService.ts`,
  `conversationPreviewUtils.test.ts`). None ship under this exception.
- The 14 mobile / 3 backend shared-contract TypeScript errors — separate
  release-hardening track, pre-existing, untouched.

### What did not pass, and why it does not block closure

**Criterion 11 — notification tap routes to the correct destination: FAILED.** The tap opens
the app but lands on the Chats list rather than the conversation.

This exposed an **independent client-side navigation defect**, not a residue of the backend
outage. Message pushes are sent as an FCM `notification` payload, so the system renders them
when the app is killed; the tap handler is registered through expo-notifications, which never
owns that intent. **No further production backend mutation can resolve it** — the fix is in the
mobile client, and the working pattern already exists in the repo for calls.

The defect is transferred to **`PALE-DEF-001`** in `Software/Pale/docs/quality/defect-registry.md`
and gated on **build 145**. It is tracked, not dismissed.
